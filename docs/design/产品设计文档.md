## 1. 产品概述

### 1.1 愿景

把「记一件事」做到 8 秒内完成、且一次输入同时产出钱与热量两个结果——让个人生活记录第一次拥有统一的日期仪表盘：今天的钱、热量、运动、待办、计划进度一屏汇总。体验优先：动效与主题不是装饰而是信息层；隐私优先：数据本地优先、全量可导出、原图不落服务端。

### 1.2 一句话定位

**「记一件事，钱和卡路里一起入账。」**

拆开讲四件事：

1. **录入摩擦极低**：写 / 说 / 拍三通道，最近记录 chip 复记 ≤5 秒；
2. **一条记录双产出**：AI 同时解析热量（含宏量与份量）与金额（含分类与账本建议），先给初值、标置信度、一键修正；
3. **记账是认真的**：分类、多账本、预算、周/月/年统计，交互对标一木记账 / iCost；热量与钱共用「收入-支出-结余」心智（kcal 账本）；
4. **一切围绕日期**：日期仪表盘是唯一首页，无第二个首页。

### 1.3 目标用户

| 画像 | 占比假设 | 现状与工具 | 核心痛点 | 付费心智 |
|---|---|---|---|---|
| A 记账人 | ~60% | 已用钱迹 / 一木 / iCost，有分类记账习惯 | 想管住吃的，但不想再开一个健康 App；热量与钱两本账对不上 | 买断（98-128 元终身，一木/钱迹锚点） |
| B 健康人 | ~30% | 用薄荷 / 好轻记饮食 | 不知道一顿饭花了多少钱、伙食预算超没超 | 订阅（12-18 元/月，健康类锚点） |
| C 计划控 | ~10% | 滴答清单 / 时光序用户 | 计划与「实际发生」割裂，一天的全貌散在 3 个 App | 跟随 A/B |

共性：中文用户、25-40 岁、城市、每天 3-5 条记录频率、**Android 优先**（国内市场盘子 + 开发机无 Mac，Android 先行上架）。

### 1.6 商业化与合规底线

- **免费档**：完整本地功能免费（记账/健身/待办不限量）+ 每日 3 次 AI 扫描额度（行业惯例口径，上线前实测复核）。
- **双轨付费**：Pro 买断 98-128 元终身（锚一木 98 / 钱迹 128）+ AI 能力订阅 12-18 元/月。定价透明、无隐性续费（直接回应 Cal AI 定价混乱痛点）。订阅必须走 IAP（App Store 计费合规前置）。
- **合规底线**：健康+财务数据合并属高敏数据，PIPL/GDPR 自查、算法备案材料、软著申请在 W7-W8 启动（备案/软著周期常达数月，必须提前）；照片云解析显式授权、**原图不落服务端（解析后即焚）**；raw_input 云端存储可关。

## 2. 核心概念与用户旅程

### 2.1 三个核心概念

**① 一件事（Entry，事件主干）**：一切记录的原子。一次输入=一条事件：何时（date/occurred_at）、何事（title）、怎么来的（source: 写/说/拍/复记/手填）。吃了兰州拉面、跑了 5 公里、买了双鞋，都是一条事件。

**② 产出行（entry_lines，facet 行）**：一件事拆出的维度行——热量行、金额行、消耗行。**每行独立变更、独立同步**：手机改金额、平板改热量，是两行各自的变更，多数同步冲突被数据结构消灭而非算法补丁。热量与金额不是两个模块，而是同一条事件的两类产出行——这是产品差异化的物理落点。修正不删旧行：新增一行引用旧行（correction_of），历史永不改写。

**③ kcal 账本**：热量就是币种。热量预算=收入，吃=支出，运动=再入账。真实钱账本与 kcal 账本共用同一套「收入-支出-结余」心智——记了钱的人天然懂热量，记了热量的人天然懂钱。

边界声明：事件模型只覆盖**已发生之事**（吃/练/花钱）。计划族（待办、健身计划、存钱目标）是独立实体族——「未来之事」不硬塞进事件模型（评审明确指出「一切皆事件」对待办/计划语义偏拧），仅在与当日记录联动时按需生成事件。

### 2.2 统一事件模型叙事（数据如何流动）

```
输入（写/说/拍）
   │
   ▼
entries（事件主干：何时/何事/来源/状态）
   │ 1:N
   ▼
entry_lines（产出行）
   ├─ calorie 行：amount=kcal，挂 food_items 菜品明细，带 confidence
   ├─ money 行：amount=分，挂 ledger/category，确认后不可变
   └─ burn 行：amount=kcal，来自 fitness_sessions
   │
   ├── 修正 → 新增行（correction_of 引用旧行）+ corrections 审计行（字段级）
   │
   ▼ 本地聚合（永不存储到服务端、永不同步）
day_summary（当日投影：kcal_in/out、支出/收入、待办完成度）
   → 仪表盘卡片墙直出、统计报表、预算余量
```

单一真值永远是明细行；聚合层永远可从明细行重建（自愈）；修正历史（corrections）是个人校准数据资产，反哺 AI 提示词（P2 闭环）。

### 2.3 一天的使用动线（7 步，全程零模态阻断、零等待空屏）

| 步 | 场景 | 量化标准 |
|---|---|---|
| 0 | **冷启动**：上一帧聚合快照直出（当日热量/支出/待办），日期大字 spring 展开、卡片墙 80ms 级联上浮，全程无 spinner | ≤1.2s 到可交互 |
| 1 | **入口**：底部中央「+」或任意页下拉 → 录入抽屉弹簧弹出（写/说/拍三通道 Tab + 最近 3 条 chip） | ≤280ms 到可输入 |
| 2 | **输入**：例「中午吃了兰州拉面花了 18」；或点 chip 复记同款；或点「仅记钱/仅记热量」单边开关 | 文字 P50 ≤3s；语音 ≤5s |
| 3 | **AI 解析**：输入气泡立即上浮不等 AI；抽屉原地转为确认卡——热量环 sweep 填充 + 金额 count-up 滚动，置信度三色点（≥0.8 绿 / 0.5-0.8 黄 / <0.5 红） | 骨架出现 ≤100ms；P50 1.5-2.5s |
| 4 | **先拍后改**：份量滑杆 1.0→1.5 热量环实时重算、金额点改、分类九宫格快选；每处修正写 corrections | 修正 ≤2 次点击 |
| 5 | **确认落库**：卡片 Hero 飞入仪表盘对应槽位，热量环 spring 推进、「今日还能吃/还能花」数字滚动 | 全程 ≤450ms |
| 6 | **后台静默**：写 Drift → sync_outbox 入队 → 后台出队同步 → day_summary 重算当日 | UI 零等待 |
| 7 | **回看**：仪表盘即历史，左右滑切任意一天的双维记录 | 切日 ≤280ms |

**北极星与漏斗纪律**（W8 内测起每周周报）：
- 北极星：**次日留存**（动效与零等待是留存第一杠杆）；
- 护栏：文字路径打开→确认 **≤8s（P50）**、拍照路径 ≤15s；
- 录入漏斗逐步流失（打开→输入→解析→确认）逐周追踪，不达标先修动线、不加功能。

### 2.4 高频摩擦的三个便宜答案（评审胜出点，全数保留）

1. **最近记录 chip 复记 ≤5 秒**：录入抽屉顶部展示最近 3 条高频记录，一键带入（日期刷新到今天、份量金额可微调）。常吃常花项是最高频场景。
2. **仅记钱 / 仅记热量单边开关**：承认不是每条记录都双产出。买本书只有钱，喝杯黑咖啡只有热量。降低录入心智负担，纯记账用户不被热量字段骚扰。
3. **解析失败自动降级手填**：AI 超时/失败 → 原输入保留，自动降级为手填表单，输入页**永不卡死**。AI 是增强而非依赖。

## 3. 功能需求（P0/P1/P2）

分级纪律：**P0 清单在 W1 冻结**（评审胜出点），冻结后新增需求一律进 P1/P2 排期，不得挤占 MVP。P0=W1-W10 上架必需；P1=V1 期（W11-W16）补齐，其中标注「留存钩子」的三项**不晚于公测后一个月**；P2=V2 期（W17-W24 起）。

### 3.1 P0 红线清单（W1 冻结，共 13 项）

### 3.4 记账与统计（分类/多账本/报表）

## 5. 数据模型

### 5.1 通用约定（W1 随 schema v1 冻结）

| 约定 | 内容 |
|---|---|
| 主键 | `id` = UUIDv7（TEXT 存储，时间有序，天然同步友好） |
| 公共列（所有同步表） | `created_at` / `updated_at`（UTC 毫秒 INTEGER）、`deleted_at`（软删墓碑，NULL=未删）、`hlc`（TEXT，定宽 HLC 编码，见 §6.3）、`revision`（INTEGER，本地自增起步、同步升级为服务端版本）、`schema_ver`（INTEGER，行级 schema 版本，默认 1）、`device_id`（TEXT，最后写入设备） |
| 金额 | 一律 INTEGER 最小货币单位（分）；kcal 一律 INTEGER |
| 日期 | `date` = 本地日历日 TEXT `yyyy-MM-dd` + `tz_offset_min` INTEGER；一切聚合按 date 分组，杜绝 UTC 错日 |
| 删除 | 软删墓碑，双端对齐后保留 90 天物理清理（GC） |
| 派生量 | 日汇总/余额/目标进度**永不存储到同步表、永不同步**，本地投影重建（见 §6.5） |

表分组：**同步真值表 14 张**（entries、entry_lines、food_items、ledgers、categories、budgets、todos、fitness_sessions、fitness_plans、exercise_sets、savings_goals、savings_contributions、corrections、theme_profiles）+ **本地件 5 张**（day_summary 投影、ai_parses 缓存、sync_outbox、sync_cursors、settings）+ **服务端为主 2 张**（devices、attachments 引用登记）。Drift schema v1 共 21 张，`schemaVersion` 只加不改，v1-v3 冻结期禁破坏性迁移。

### 5.3 facet 拆行的同步正确性说明（评审必修项的落点）

「同一条事件的多维度」拆成**行**而非**列**：手机端改金额、平板端改热量，产生的是**两行各自的 updated_at/hlc**，同步合并互不覆盖——多数冲突在数据结构层被消灭，而非靠 LWW 算法补救。同 facet 行同字段并发才是真冲突，交给行级 LWW（§6.5）。这是放弃「entry_items 宽表」（评审指出其多端并发改不同字段会整行覆盖）的根本原因。

## 6. 同步设计

### 6.1 四条原则

1. **本地优先**：UI 零网络依赖，无网全功能可用，离线队列无上限，同步失败仅顶栏小圆点提示、永不阻塞。
2. **append-first**：能只增不改的绝不改行（修正、贡献、审计）——从结构上消灭冲突。
3. **投影不同步**：聚合/统计/余额/进度永不存储于服务端，双端从明细行各自重建——单一真值永远是明细。
4. **可导出可自毁**：数据主权，全量导出+一键清空；服务端选型必须是数据可整体迁出的（托管 Supabase 可 pg_dump 迁自托管）。

### 6.2 架构与读写路径

```
【写路径】UI → Drift 事务提交（业务行 + sync_outbox 同事务写入，同步返回）
        → SyncEngine 后台出队 → POST /rpc/sync_push（幂等键 = outbox.id）
        → 服务端校验（schema_ver / 行存在性 / hlc 单调）→ 签发权威 seq
        → 本地回写 revision / acked_at

【读路径】GET /rpc/sync_pull?since_hlc=…（per-table 游标）
        触发时机：启动即拉、前台切回、（可选）Realtime 推送、后台 15 分钟兜底
```

- 客户端：Drift 主库 + sync_outbox + **SyncEngine 抽象层**（接口 `push(batch) / pull(since) / resolve()`）——评审胜出点：抽象成可换 PowerSync/CRDT 而**不动 schema**。
- 服务端：托管 Supabase（Postgres + Auth + RPC）。表结构与 Drift schema 同构（由 Drift schema 生成 SQL 迁移，单侧定义双侧生成，杜绝漂移）；RLS 按 user_id 行级隔离；op seq（BIGSERIAL）+ outbox.id 唯一键保证幂等（重试不重复入账）。

### 6.3 HLC 混合逻辑时钟（含定宽编码修复——评审必修项）

**定义**：hlc = (physical_ms, counter, device_id)。
- 物理部分 = max(本地墙钟, 已见最大物理值)；同一毫秒内 counter 自增；
- 收到比本地新的时间戳 → 跳变跟上；收到比本地旧的 → 沿用本地物理并 counter++；
- **时钟回拨**：物理部分取 max，回拨不影响全序；回拨过大（>60s）上报告警。

**定宽编码（修复评审指出的「999 与 1000 字典序颠倒」隐藏 bug）**：字符串必须字典序=时间序，裸十进制不满足。编码规则：

| 段 | 宽度 | 说明 |
|---|---|---|
| physical_ms | 13 位十进制补零 | 10^13 ms ≈ 公元 33658 年，够用 |
| counter | 6 位十进制补零 | 单 ms 上限 999,999 次事件，超限物理+1 进位 |
| device_id | 12 位定长 | UUIDv7 前 12 个 hex 字符 |

最终形如 `0001700000000000:000042:3F8A12C0B7D4` —— **字典序即全序**，SQLite / Postgres 均按 TEXT 比较即得 LWW 顺序。单测进 CI：进位边界（…999 < …1000）、回拨、跳变、同 ms 并发四用例。

### 6.4 schema 演进

- **行级 schema_ver 只加列前向兼容**：老客户端忽略新列；新客户端写默认值；同步层按 schema_ver 协商容忍 N-1。
- **破坏性变更**：新表并存 + 双写过渡 + 全量重拉重建本地库（本地库可随时从服务端全量重建）。
- v1-v3 冻结期禁破坏性迁移；同步协议字段（hlc/schema_ver/deleted_at/revision）在 W1 冻结，先于 UI。

### 6.5 冲突解决矩阵（按实体分级，边界诚实写明）

| 实体类 | 策略 | 语义与边界（明示代价） |
|---|---|---|
| 标量配置（settings / theme_profiles） | 行级 LWW（hlc 大者胜，同刻 device_id 决胜） | 并发改同一配置=后写者胜，先写改动丢失——标量无法合并，接受 |
| entries 事件主干 | 行级 LWW + 字段保留集 | corrections 引用的历史字段永不覆盖；status=draft 时 AI 字段可被新解析覆盖。诚实边界：**离线多端同改同一条 entry 的不同字段（如一端改 title、另一端改 date）=行级 LWW 后写者胜，先写方该字段改动丢失**——低敏描述字段（title/note）接受；金额与热量等高敏字段已由 facet 拆行（§5.3）隔离在不同 entry_lines 上，不经此路径丢失 |
| entry_lines 产出行 | **facet 拆行结构性免冲突为主**；同 facet 行同字段并发=hlc LWW | 手机改金额/平板改热量=两行独立变更，无冲突（§5.3） |
| money 行（confirmed 后） | 不可变，修正=新增 correction 行 | 并发合并=并集，零冲突 |
| corrections / savings_contributions | append-only 并集 | 天然零冲突 |
| todo.done | 完成事件只前进 | 并发 set vs unset：set 胜（勾选永不丢失）；取消完成仅无并发时生效 |
| 删除 | 墓碑拒绝复活 | 删后编辑保持删除胜出；墓碑 90 天 GC |
| day_summary / 统计 / 余额 / 目标进度 | **不同步** | 派生量不存在于服务端，双端从明细重建，永远自愈 |

### 6.6 端到端加密（P2，默认关）

随机生成库级 DEK → 用户口令 Argon2id 派生 KEK → DEK 密文托管服务端；云端只见密文与墓碑；**改口令=重包 DEK 不重加密数据**；恢复码离线备份（密钥丢失不可恢复，导出文件为兜底）；附件 content_hash 去重 + 加密 blob + 行内引用。实现选纯 Dart（XChaCha20-Poly1305 + Argon2id）——开发机无 Rust，全依赖链禁 Rust FFI。

### 6.7 验收自动化（CI 硬闸门，评审胜出点）

| 用例 | 通过标准 |
|---|---|
| 双设备一致脚本 | 两台模拟器/设备各本地新增 100 条（含离线期）→ 开网双向同步 → 逐行比对一致率 100% |
| 飞行模式回归 | 录入→确认→统计→切日全流程断网可用 |
| 冲突测试集四用例 | 时钟回拨 / 双端离线新建 / 删后编辑 / 两端同改同字段——预期结果断言进 CI |
| HLC 单测 | 定宽编码进位、回拨、跳变、同 ms 并发 |

## 7. AI 解析管线

### 7.1 管线总览

```
输入（文本 / 语音转写 / 照片端侧压缩：长边 1280、JPEG q80）
  → 规范化 + input_hash（sha256）
  → 缓存命中（ai_parses <7 天）？命中则直接复用 raw_output
  → LLM adapter（OpenAI 兼容协议，可插拔）
  → JSON Schema 受约束解码（拒绝自由文本）
  → 校验器（金额>0、kcal∈[0,5000]、分类枚举内、必需字段齐）
  → 食物库联查校准（USDA CC0 + OpenFoodFacts ODbL 文本快表；拍照 P1 百度菜品识别 9000+ 中文菜品）
  → 确认卡（置信度三色点 + 可编辑字段）
  → 用户确认/修正 → 落库（entries + entry_lines + food_items + ai_parses + corrections）
```

红线：**LLM 直报热量不可信**（学界基准 GPT-4o 餐级误差约 55%、商业自报口径 ±15%、中餐油量/份量失准更甚）——必须走「结构化输出 + 食物库联查 + 置信度标注 + 一键修正闭环」管线，把信任设计做成一等交互而非补丁。

### 7.4 降级方案（健壮性即产品体验）

| 场景 | 行为 |
|---|---|

### 7.5 成本估算（2026-11 牌价口径，上线前必须实测复核）

| 环节 | 供应商/模型 | 单价口径 | 单次成本估算 | 用途 |
|---|---|---|---|---|

## 8. 主题与样式自定义系统

### 8.1 设计原则

主题自定义是用户数据的一部分（theme_profiles 参与同步、换设备主题跟随），而动效与主题同源同发（MotionConfig 挂进主题，§9.2）。双主色语义锚定保证「换主题不换认知」。

### 8.2 设计 token 三层架构

```
第 1 层 原始色板：种子色 → material_color_utilities HCT tonal palette（自动生成 0-100 色阶）
第 2 层 语义 token：SlimcaTheme extends ThemeExtension<SlimcaTheme>
第 3 层 组件：只引用语义 token；lint 禁止裸色值/裸时长（ui_kit 只导出语义组件）
```

语义 token 清单：

| token | 语义 |
|---|---|
| surface / surfaceMuted / surfaceCard | 背景层级 |
| primary / onPrimary | 品牌主色（交互锚点） |
| kcalIn / kcalOut / net | 热量语义——**双主色锚定：健康绿=热量** |
| moneyIn / moneyOut | 金额语义——**双主色锚定：暖橘=金额** |
| success / warn / danger | 状态（含置信度三色点复用） |
| radiusScale / density / fontScale / motionScale | 形状/密度/字重/动效强度滑杆 |

双主色锚定规则：健康绿（热量）与暖橘（金额）的**色相在所有主题包中固定**，只允许调明度/饱和度——用户换任何主题，「绿是吃、橘是钱」的认知不变。

### 8.3 实现机制

- `SlimcaTheme extends ThemeExtension<SlimcaTheme>`，含 14+ 语义字段；`ThemeExtensionTween` 自实现 lerp。
- 主题切换 = `ColorScheme.lerp` + `ThemeExtensionTween`，全屏 morph 300ms 无闪跳（本身就是十条关键转场之一）。
- 主题包 = JSON profile（tokens + 字体 + motion_level），存 theme_profiles 表（同步真值）；6 套内置包：墨 / 纸 / 霓虹 / 奶油 / 森野 / 曜黑（AMOLED 纯黑独立开关）。
- **dynamic_color**（Android 12+ Material You）：仅映射 primary/seed 两源（不整体套用系统色，保品牌识别与双主色锚定）；iOS/旧机型回退手动种子色。
- 深浅色：跟随系统 + 日落定时切换；浅深各自过对比度校验。
- **WCAG AA 对比度校验**：主题编辑器实时校验关键前景/背景对（正文、金额、热量数字），**不达标的主题包禁止保存**；6 包 × 深浅色全部进 golden 快照回归（仅 Linux CI 基线，规避 Windows 字体渲染差异——评审胜出点）。
- 可及性：动效强度滑杆 0.6x-1.5x，尊重系统「减弱动态效果」（自动降至 0.6x 并去视差/去模糊）。

### 8.4 主题编辑器（P1）

| 能力 | 说明 |
|---|---|
| 种子色取色 | 从照片取色或色轮选择 → HCT 色板实时生成 |
| 对比度护栏 | WCAG AA 实时校验，不达标红字提示且禁止保存 |
| 形状密度 | 圆角/密度/字重/动效强度四滑杆 |
| 实时预览 | 仪表盘/流水/确认卡三个关键页面实时换肤 |
| 命名与同步 | 自定义包命名入库，随 theme_profiles 同步到所有设备 |

## 9. 动效系统

### 9.1 定位与物理前提

**动效不是装饰而是信息层：每个动效必须回答一个问题——数据去了哪、变化了多少、什么状态变了；回答不了的动效删掉。** 物理前提：Impeller（Flutter 3.32 默认开启）消除 shader 编译卡顿——这是动效卖点的成立条件。

### 9.2 MotionConfig（动效 token 挂进主题）

| token | 值 | 用途 |
|---|---|---|
| dur.xs | 60ms | 微反馈（按压涟漪） |
| dur.s | 120ms | chip / 勾选 |
| dur.m | 180ms | 卡片上浮级联间隔 |
| dur.l | 280ms | 抽屉 / 页面 / 共享轴 |
| dur.xl | 450ms | 落库飞入 / 容器变换 |
| spring.snappy | 220ms，阻尼比 1.0 | 交互跟随（不回弹） |
| spring.soft | 400ms，阻尼比 0.85 | 容器变形 / 环推进 |
| MotionLevel | off / reduced / full | 用户可调；off=全部转场降为 100ms 淡入淡出；尊重系统「减弱动态效果」 |

所有动效只引用 token 不写裸值（lint 强制）；隐式动画仅限微交互。

### 9.5 工程约束

- 路由级转场一律显式 PageRouteBuilder；隐式动画仅限微交互。
- 列表用 AnimatedList/自定义 FLIP，禁 setState 全列表重建；图片 pre-cache；动效期间禁主线程 JSON 解析。
- TickerMode 离屏暂停 + RepaintBoundary 隔离重绘区域。

### 9.6 降级阶梯与测试（评审胜出点）

- **降级阶梯**：连续 3 帧丢帧 >16ms → 依次关闭 stagger → 关粒子 → 仅保 Hero；MotionLevel=off 时全部转场 100ms 淡入淡出。
- **golden 关键帧**：每条关键转场配 0% / 50% / 100% 三关键帧快照（比逐帧快照稳健）+ frame benchmark 进 CI；golden 仅在 Linux CI 基线生成（规避 Windows 字体渲染差异）。
- 动效不合格不得合并（CI 红即打回）。

## 10. 技术选型

### 10.1 推荐栈

| 层 | 选型 | 关键理由 |
|---|---|---|
| 框架 | **Flutter 3.32.0 stable + Dart 3.8.0**（Impeller 默认开启） | 与开发机实测版本一致；单栈双端（竞品多仅 iOS）；Impeller 消 shader 卡顿=动效卖点的物理基础 |
| 状态 | Riverpod 3 | 编译期安全；AsyncNotifier 天然适配离线队列与流式 UI |
| 路由 | go_router（StatefulShellRoute） | 承载 4 Tab 各自导航栈；可注入自定义 PageRouteBuilder |
| 数据 | Drift 2.x（SQLite） | 活跃维护（对比 Isar/Hive 均停更）、类型安全、SQL 聚合正合 day_summary 投影与统计报表、reactive stream 直驱仪表盘 |
| 后端 | **托管 Supabase**（Postgres+Auth+Realtime）起步 | 零运维起步；RLS 行级隔离；数据自持可整体 pg_dump 迁自托管（Triplit/ElectricSQL/Realm 停更前车之鉴） |
| 同步 | 自研 outbox+HLC（§6），SyncEngine 抽象 | 可换 PowerSync/CRDT 而不动 schema；PowerSync 为备选，FSL 许可过法务前不引入 |
| AI | OpenAI 兼容协议 adapter：GPT-4o-mini / Qwen-VL / GLM-4V | 可插拔+国内已备案通道；JSON Schema 受约束解码 |
| 语音 | 端侧 ASR（iOS Speech / Android SpeechRecognizer）+云兜底 | 转写零成本、隐私友好 |
| 加密 | XChaCha20-Poly1305 + Argon2id，纯 Dart | 开发机无 Rust——**全依赖链禁 Rust FFI 扩展**（P2 E2E） |
| OCR | ML Kit（Android）/ Vision（iOS）端侧 | 不传原图（对比云端 OCR 隐私劣势） |
| 动效 | flutter_animate（时序链）+ 自研单自由度弹簧（参数入 MotionConfig）+ Rive（状态机）+ CustomPainter（环/图表） | token 化治理 |
| CI | GitHub Actions：analyze+test+Android debug APK+golden（Linux 基线）+帧预算 benchmark；iOS 签名上架走 Codemagic 云 Mac | 本机无 Mac 的现实路径 |

### 10.2 备选对比（关键三项）

| 选项 | 对比结论 |
|---|---|
| Flutter vs React Native | RN 新架构桥接开销对「满动效+帧预算硬指标」的打磨成本更高；Flutter Impeller+自定义转场生态更成熟 → Flutter |
| Drift vs Isar/Hive vs sqflite | Isar/Hive 已停更（调研确认）；sqflite 裸 SQL 无类型安全；Drift 活跃+schema 迁移体系完整 → Drift |
| 托管 Supabase vs PowerSync vs Firebase vs 自研全托管 | Firebase 数据不自持+国内不稳；PowerSync FSL 许可未过法务；自托管压进一期运维过重（评审明确单人运维成本最小化顺序：托管起步、自托管/E2E 后置 P2）→ 托管 Supabase |
